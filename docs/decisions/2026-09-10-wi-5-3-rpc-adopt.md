### Role in the system

The RPC surface is the bridge between pi-crew (extension) and other
Pi extensions that want to drive or observe pi-crew runs. Removing it
would break:

1. The cleanup path (`runtime-cleanup.ts` 107, 185) — currently calls
   `ctx.rpcHandle?.unsubscribe()` on session teardown. Without the
   handle, dangling RPC subscriptions could fire into a dead context.
2. The cross-extension wiring (`wire-cross-extension.ts`) — the
   registration path is the only entry that exposes pi-crew's event
   stream to other extensions.

## Verdict

**KEEP** — the surface is actively used by the registration lifecycle.

## What "adopt" means here

Per spec language "adopt-or-retire": if a 0-consumer surface exists,
remove it. If active, document it.

Action items:

1. **Document** the surface in `docs/extension/rpc.md` (NEW; lightweight):
   - API contract (PiCrewRpcHandle + HMAC scheme)
   - Consumer list (3 internal call sites above + 1 doc ref)
   - Migration story if HMAC version bumps
   - Failure mode if `rpcHandle` is undefined
2. **Add a contract test** that asserts `ctx.rpcHandle?.unsubscribe()`
   is called on both session-time cleanup paths.

The test addition is the highest-leverage deliverable for WI-5.3 —
it makes the "active in cleanup" claim verifiable, not just grep-able.

## What "adopt" does NOT mean

- No new RPC methods added in this window.
- No version bump of `RPC_HMAC_VERSION` (`rpc-hmac.ts:17`).
- No change to the HMAC soft-info emission policy
  (`rpcHmacSoftInfoOnce` at `:63`).

## Negative consequences of KEEP

- 610 LOC of "infrastructure for cross-extension use" carries in the
  bundle. `dist/index.mjs` would shrink ~610*4=~2.4 KB unminified if
  removed (a trivial win for size, but not enough to justify breaking
  the cleanup path).

## Re-evaluation triggers

This ADR is superseded when:

1. The full wiring is no-op'd (no extension uses PiCrewRpcHandle) →
   candidate for REMOVE.
2. RPC_HMAC_VERSION bumps AND the migration path requires re-design.
