## Problem

pi-crew runs in CI (`.github/workflows/ci.yml` runs gates locally) but a
pi-crew TEAM run's result has no way to land on the PR: reviewers must open
the run dir on the runner (which is gone after the job).

## Goals / Non-goals

- Provide a small, documented CI entry point that runs a pi-crew team
  command and posts the run report (markdown, from US-022) as a PR comment
  (create-or-update one comment, not spam).
- Ship as a **reusable GitHub Actions workflow snippet + a thin CLI path**
  in pi-crew (no runtime dependency on an Actions SDK; use `gh` or the REST
  API via `fetch`).
- NOT in scope: hosted service, matrix of PR events, review-comment
  threading.

## Design

Anchors: `src/extension/run-export.ts` (markdown report — the comment body),
`.github/workflows/` (where the reusable snippet lands),
`src/extension/team-tool.ts` (a headless CLI entry already used by CI tests
— confirm and reuse).

Proposal:

1. `docs/ci/github-actions-example.yml` — a workflow that runs
   `pi-crew ... action=run ...` headlessly, then posts the exported
   markdown.
2. `scripts/gh-pr-comment.mjs` — finds an existing comment with a marker
   (`<!-- pi-crew-report -->`) and updates it, else creates; uses
   `GITHUB_TOKEN` + REST API via `fetch`; no new deps.
3. Document required permissions (`pull-requests: write`) and secret
   handling (never print tokens; redact like `redactHomePaths`).

## Acceptance Criteria

1. Example workflow is copy-paste runnable (validated by `actionlint` in the
   repo's own CI, or a YAML parse test).
2. Comment script: create-if-absent, update-if-present (test with a stubbed
   API returning an existing marker comment).
3. Token never appears in any output (test greps the script's stdout given a
   token env).
4. Failure to comment does not fail the run job (warning + exit 0 with a
   documented flag to hard-fail).
