# US-002 — Structured run-level lock cleanup

## Status

planned

## Lane / Priority

normal · P2

## Source

- `docs/stories/backlog.md` — Reliability epic, US-002 (planned).

## Problem

Run-level coordination locks block progress on correctness (the RR wave fixed
ownership semantics — see `docs/decisions/` for F02/F03/F15 — but not the
lifecycle of the lock artifacts themselves). Current state:

- `src/state/coordination/locks.ts` — `withRunLock` family, `sleepSync`
  busy-wait retry inside (10 `sleepSync` references in this file alone per
  2026-09-22 grep).
- Locks are acquired per `(runId, owner)` and released on success/error
  paths, but there is **no structured sweep** for locks whose owner dies
  without releasing (crash, kill -9, SIGKILL of the holder).
- `src/runtime/stale-reconciler.ts` exists for run state; locks are not part
  of its sweep.

## Goals / Non-goals

- Add a structured, safe, idempotent lock-cleanup sweep: locks owned by
  dead sessions/processes are released.
- Never break the "exactly one owner at a time" invariant (F02) — a dead
  owner's lock is only releasable after we can PROVE the owner is dead
  (async.pid `process.kill(pid, 0)` probe, the same proof run-index uses at
  `src/extension/run-index.ts:58-66`).
- NOT in scope: changing the locking protocol (still async-context owned).

## Design

Anchor: `src/state/coordination/locks.ts` (lock table), the stale-reconciler
sweep hook point.

Proposal — add to the existing stale-reconciler pass a lock sweep:

1. Iterate live lock entries; each carries `{ runId, ownerSessionId?, pid?,
   acquiredAt }`.
2. If the entry has a `pid`: `process.kill(pid, 0)` probe — PID dead ⇒
   release. PID alive ⇒ keep.
3. If the entry is session-owned but the session is not in the live-session
   registry ⇒ keep for a quiescence TTL (the session may be mid-restart),
   then release.
4. Release = `delete` + a `lock.released_stale` event (observability).

## Acceptance Criteria

1. A lock recorded with a dead PID is swept within one reconciler tick.
2. A lock recorded with a live PID is never swept (fuzz test: N concurrent
   holders, none released erroneously).
3. A session lock whose session is absent is swept only after the quiescence
   TTL, never immediately.
4. Sweep is idempotent: two concurrent sweeps release each stale lock once
   (second is a no-op).
5. Release path logs to the run's event log + `pi.events` (same channel as
   other reconciliation).

## Notes

- Reuse the `async.pid` read pattern already in `run-index.ts` — do not
  invent a second mechanism.
- Document the sweep in `docs/decisions/` (owner-death proof = PID probe +
  session quiescence, matching the existing ownership ADR).
