# DP-01 — Auto-prune retention guards (age-floor, env keep, audit rotation)

## Status

planned — **P1, highest-value item in this backlog** (three independent
data-loss incidents in one session).

## Lane / Priority

normal (but touches data lifecycle → treat as high-risk for defaults) · P1

## Source

- `docs/stories/backlog.md` — "Deferred — performance deep-dive 2026-09-18".
- Session evidence 2026-09-21/22 (below).

## Problem

Auto-prune runs at **every extension/session start**
(`register.sessionStart.autoPruneProject` / `autoPruneUser`,
`src/extension/registration/lifecycle-handlers.ts:466-495`; audit writer
`src/extension/run-maintenance.ts:112`) with a hard-coded **keep=10**.

Measured damage:

1. **Battery evidence destroyed.** A morning of real-test evidence runs
   (T7 smoke + review runs) was deleted by the next session start —
   `.crew/audit/prune.jsonl` shows `removed=14` at 14:37:28Z, including the
   goal-loop turn run `team_20260921111307_7be4a51df04c844d`.
2. **Failure reasons destroyed.** The GL-1b incident
   (`goal_20260921111305…`): the only copy of the turn-failure reason lived
   in the pruned turn dir → the goal stayed "blocked" with no explanation
   (fixed at goal level in `2f0f4c67`, but the underlying retention hole
   remains for every other failure).
3. **Audit log unbounded.** `prune.jsonl` reached 720 KB / 1,436 entries
   with no rotation.
4. **No intent/attribution** on auto-prune entries — you cannot tell which
   session pruned what, or why.

## Goals / Non-goals

- **Age-floor**: never auto-delete a FINISHED run younger than N hours
  (default 24) even if it falls outside top-keep. Manual prune/forget
  unaffected.
- **`PI_CREW_AUTO_PRUNE_KEEP`** env (default 10) — mirrors the
  `PI_TEAMS_HOME`/`PI_CREW_HOME` env convention in `src/config/env-vars.ts`.
  Reject non-numeric/negative (same guard style as `userPiRoot`'s
  `"undefined"` defensive check).
- **Audit rotation + size cap** for `prune.jsonl` (e.g. rotate at 512 KB,
  keep 3 files) — reuse the `forEachLineSync` pattern from
  `event-log-rotation.ts` rather than a new mechanism.
- **Intent + attribution** fields on auto-prune audit entries:
  `{ action, keep, kept, removed, auditedAt, intent: "session-start-auto",
    sessionId?, reason?: "age-floor" | "keep" }`.
- **Failed-run summary preservation**: when pruning a run whose
  `manifest.status` is `failed`/`blocked`, append one line to a durable
  index (`<crewRoot>/state/pruned-failures.jsonl`): runId, status, summary
  first line, createdAt, prunedAt. Makes failures recoverable post-prune.

## Design

Anchors:

- `src/extension/registration/lifecycle-handlers.ts:466-495` — the two
  auto-prune entry points.
- `src/extension/run-maintenance.ts:112` — `appendPruneAudit`.
- `src/extension/team-tool/lifecycle-actions.ts` / `handlePrune` — the
  manual prune path (should stay unguarded by the age-floor by default, or
  expose `--ignore-age-floor` explicitly).
- Evidence of the current behavior: `.crew/audit/prune.jsonl` (1436 lines).

Shape:

```
autoPruneProject(ctx, { keep: envKeep(), ageFloorHours: envAgeFloor() })
  → candidates = finished runs sorted newest-first
  → protected = candidates where age < ageFloor  (never removed by auto)
  → removable = candidates beyond top-keep AND not protected
  → for each removable failed/blocked run: append pruned-failures line
  → remove; audit each with intent/attribution
```

## Acceptance Criteria

1. A finished run < 24 h old is never removed by auto-prune regardless of
   keep (test: 15 finished runs, all < 1 h, keep=10 → 0 removed... wait —
   the age-floor protects only NEW runs; with keep=10 and 15 runs, 5 are
   older — verify the rule is "protected if younger than age-floor" and the
   test asserts exactly that).
2. `PI_CREW_AUTO_PRUNE_KEEP=25` keeps 25; invalid values fall back to 10
   with a warning (no crash, no infinite keep).
3. Failed/blocked pruned runs leave one recoverable summary line.
4. `prune.jsonl` rotates at the cap; audit entries carry
   `intent`/`sessionId` for auto-prunes.
5. Manual prune behavior unchanged unless the new flag is passed (regression
   test against the existing T9d recipe in the skill).
