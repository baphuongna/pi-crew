# SR-03 — Test-flake remediation (2 known flakes)

## Status

planned

## Lane / Priority

normal · P2 (gate credibility: a suite with known flakes trains people to
ignore red)

## Source

- Session 2026-09-21/22 measurements (repeated full-suite runs):
  1. `test/unit/extension/core/session-summary-cov.test.ts` — vector #11
     ("notifyActiveRuns filters out runs owned by another session"). Observed
     failing in FULL-suite runs; passes **4/4 in isolation** (reproduced
     twice, 2026-09-22).
  2. `test/unit/runtime/subagent-tools-integration.test.ts:929` — known flake
     (noted in the real-test skill's symptom table).

## Problem

Both flakes are timing/concurrency-sensitive: they fail only under the
4-way parallel runner, never alone. Cost: every full-suite run has a
non-zero chance of a red that is not a real defect → wasted re-runs and
reduced trust in the gate (the exact opposite of what the RR-015 test-
integrity wave was for).

## Goals / Non-goals

- Identify the ROOT CAUSE of each flake (do not paper over with retries
  first). Likely candidates: shared on-disk state between tests (temp dirs,
  user-root leakage), real-clock dependence, or a cross-test global.
- Fix root cause if reachable; if genuinely irreducible scheduling, isolate
  the test (own file + serial) and document WHY in the file header.
- NOT in scope: adding a blanket retry to the runner (masks real bugs).

## Design

Per flake:

1. **Reproduce deterministically**: run the file with the full-suite
   concurrency (`--test-concurrency=4`) repeatedly, or run the whole suite N
   times, capturing the failure output. A flake you cannot reproduce is not
   fixable — invest in reproduction first (e.g. run the file alongside its
   likely neighbour files).
2. **Triage**: for `session-summary-cov` #11 (`notifyActiveRuns` filters by
   session) — check whether the test relies on the REAL user root / real
   home (env isolation pattern is `PI_CREW_HOME` + delete `PI_TEAMS_HOME`,
   see `manifest-cache-list-active.test.ts:23-45`). If the test does not
   isolate env, another test's state can leak in → intermittent wrong
   filtering. That is a test bug, fix the isolation.
3. For `subagent-tools-integration:929`: inspect what it waits on; if it
   polls a real deadline, pin the clock or inject the deadline.
4. If neither can be made deterministic: mark with a precise
   `{ concurrency: false }`-style isolation plus a REQUIRED comment naming
   the root cause and the reproduction command — never a bare skip.

## Acceptance Criteria

1. Each flake has either a root-cause fix, or documented isolation with the
   reproduction evidence.
2. Evidence: N≥5 consecutive FULL-suite runs (4-way) with 0 failures from
   these files.
3. No blanket retry added to `scripts/test-runner.mjs` (assert in the PR
   diff).
4. `docs/TEST_MATRIX.md` / skill symptom table updated with the resolution.

## Validation

| Layer | Check | Expected |
|-------|-------|----------|
| Repro | N≥5 full-suite runs | 0 flake occurrences |
| Unit | both files in isolation + with concurrency 4 | green |
| Regression | no other suite turned red | 0 fail |

## Notes

- Budget-guard: if 5 full-suite runs are too slow, run the two suspect files
  WITH their likely neighbours and the full runner concurrently — but the
  acceptance still wants ≥5 full-suite passes because the flake is
  suite-level.
- A third flake class seen once (env-dependent suite subtest counts,
  8,098 vs 8,077 across runs) is NOT this spec: it is discovery-count
  variance, benign, but worth a one-line note in the skill.
