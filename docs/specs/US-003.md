# US-003 — Dead letter queue for permanently failed tasks

## Status

done (2026-09-22)

### Implementation notes (honest deviations + findings)

- A run-local dead-letter already existed (`src/runtime/deadletter.ts`,
  written at `onRetryGivenUp` — max-retries only). This spec added the part
  that matters for retention: the **project-level index**
  (`<projectRoot>/.crew/state/deadletter/<runId>.jsonl`) that survives
  run-dir pruning, plus the richer entry schema (agent/role/modelAttempts/
  runStatus) and `handleStatus` surfacing (`Deadletter: N (reasons)`).
- **AC-1 deviation**: "atomically (both or neither)" across two files is not
  physically possible without a journal. Contract implemented: both written
  by one best-effort call, each failure logged, NEVER a caller-visible throw
  (the retry path must not break). Tests cover both-on-success and each-side-
  blocked.
- **TWO REAL BUGS found while wiring the integration test** (both fixed here):
  1. The coalesced dispatch path (`run-coalesced-task-group.ts`) retried via
     `executeWithRetry` but wired NO hooks — exhausted retries on M6 groups
     were never deadlettered. Now wired, with an abort guard (see 2).
  2. **Retry-noop bug (dispatch-batch singleton path)**: a retry only happens
     because our previous attempt threw — and that throw persists the task's
     terminal `failed` state FIRST. The retry body's terminal-state guard then
     treated OUR OWN persisted failure as "nothing to do" and returned success:
     `executeWithRetry` never re-ran the task, never exhausted, and
     `onRetryGivenUp` never fired. autoRetry was silently a single attempt for
     every failure that persists task state (e.g. model-exhausted). Fix:
     on `attempt > 1`, re-queue our own terminal failure before the guard;
     attempt 1 keeps the original externally-terminal semantics.
  - Abort guard added to both paths: `executeWithRetry` fires `onRetryGivenUp`
    on its CANCELLED exit too — an aborted run is not exhaustion and must not
    deadletter as "max-retries".
- The original GL-1b fixture never exercised `retryable-failure`: it failed
  earlier at agent resolution (`Agent 'worker' not found`) because the
  goal-turn workflow dispatches role `worker` and the fixture discovered no
  such agent. Fixed by providing a synthetic worker agent (and
  `PI_CREW_ALLOW_MOCK=1` so the mock actually fails).

## Problem

Tasks that exhaust their retry budget (`attempts` / `modelAttempts` in
`TeamTaskState`; retry config e.g. `retryable-failure` mock → run-level
failure; see `src/runtime/child-pi/mock-fixtures.ts:127-131` for the
retryable-failure shape) today end as ordinary `failed` tasks inside the run.
The failure reason is only in the run's events.jsonl / task state. There is
no durable, out-of-band record for post-mortem analysis after the run dir is
pruned (`auto-prune keep=10` — see DP-01), and no mechanism to re-drive a
failed task without re-running the whole team.

## Goals / Non-goals

- When a task transitions to `failed` after exhausting retries, write a
  durable **dead-letter entry** (structured, greppable) under
  `<runId>/artifacts/deadletter/` AND optionally to a project-level
  `deadletter/` index that survives run-dir pruning.
- The entry captures: taskId, agent, retryCount, error message (first line),
  modelAttempts, mtime.
- NOT in scope: automatic re-queueing/retry orchestration (that is a larger
  change); a UI (that's US-020/US-021).

## Design

Anchor: task finalization path in `src/runtime/task-runner/` (where
`attempts` overflow marks the task failed — `runTeamTask` + retry loop), and
the artifacts writer `writeArtifact` in `src/state/stores/artifact-store.ts`.

Proposal:

1. At the point a task is set to a terminal `failed` status because retries
   are exhausted, write a dead-letter artifact:
   `writeArtifact(artifactsRoot, { kind: "metadata", relativePath:
   "deadletter/<taskId>.json", producer: "deadletter", retention: "run" })`.
2. Also append one line to `<projectRoot>/.crew/state/deadletter/<runId>.jsonl`
   (project root so it survives per-run pruning) — same schema, plus runId +
   run.status at time of write.
3. `handleList`/`handleStatus` `deadletter` sub-action (or a note in run
   status output) surfaces the count + latest entries.

Schema (one line, JSON):

```json
{ "runId": "…", "taskId": "…", "agent": "…", "role": "…",
  "retryCount": 3, "error": "…first line…", "modelAttempts": 2,
  "failedAt": "ISO", "runStatus": "failed" }
```

## Acceptance Criteria

1. Exhausted-retry failure writes the dead-letter artifact + the index line
   atomically (both or neither per task).
2. Index is append-only JSONL; a re-run of the same runId must not silently
   overwrite prior entries (append, or version the file).
3. `handleStatus` output includes `deadletter: N` when N > 0.
4. The artifact survives `forget` health checks (it is a normal artifact —
   verify nothing special needed).

- P3: implement only after DP-01 (retention guards) lands — otherwise the
  index itself argues for the very pruning the dead-letter is meant to
  survive.
- Do NOT hook general failures (non-retry) — only exhausted-retry, to keep
  the signal high.
