## Problem

GL-1b fixed diagnosability (the reason now lives at goal level and survives
pruning). But the explorer mapped four early-exit paths that leave the TURN
manifest stuck at `queued` — no failure recorded on the turn run itself:

| # | Path | Anchor |
|---|------|--------|
| a | `createRunManifest` throws | `state-store.ts:284,431-448` |
| b | `store.patch` throws | `goal-loop-runner.ts:624` |
| c | `loadConfig`/`effectiveRunConfig`/`resolveCrewRuntime` throw | `goal-loop-runner.ts:656-658` |
| d | executeTeamRun PRE-TRY throw | `team-runner.ts:347-409` (preflight import `:355`, `updateRunStatus("running")` `:372`, heartbeat `:397`) |

Paths b–d have a manifest on disk that says `queued` forever, while the goal
says `blocked`. That is an inconsistent state: a later `goal resume` or a
`team status` on that turn id reports `queued` (i.e. still running) for a
turn that is long dead. Path d is the dangerous one — `executeTeamRun` has
its own try/catch around `executeTeamRunCore` (persists `failed` at
`team-runner.ts:490-532`), but anything BEFORE that try escapes with the
manifest still `queued`.

## Design

Wrap the turn-execution call so that ANY throw between "manifest created"
and "executeTeamRun's own catch" marks the turn manifest failed before
re-throwing:

```ts
// goal-loop-runner.ts, around :654-663
try {
  …loadConfig/effectiveRunConfig/resolveCrewRuntime…
  turnResult = await executeTeamRun(...);   // its own catch handles core throws
} catch (error) {
  const msg = error instanceof Error ? error.message : String(error);
  try {
    const { manifest: loaded } = loadRunManifestById(goal.cwd, created.manifest.runId) ?? {};
    if (loaded && loaded.status === "queued") {
      updateRunStatus(loaded, "failed", `pre-execute failure: ${msg}`);
    }
  } catch { /* best-effort; the goal-level error already persisted by B */ }
  throw error;   // outer catch (B) persists lastTurnError + goal.loop_error
}
```

Explicitly guard on `status === "queued"` so we never overwrite a status the
executor already set.

## Acceptance Criteria

1. For each of paths b–d (simulated deterministically — e.g. a `deps` seam
   or a forced config failure), the turn manifest ends `failed` (not
   `queued`) and its summary carries the pre-execute message.
2. `executeTeamRunCore` failures are unchanged (they already write
   `failed` — no double-write; the guard prevents it).
3. The goal-level persistence from fix B is unaffected (still one
   `lastTurnError` + one terminal event).
4. No new throw path introduced: the wrap re-throws the original error.

## Notes

- Path (a) (`createRunManifest` throws) cannot write a manifest by
  definition; it is only covered by fix B at the goal level. State that
  explicitly in the code comment so nobody "fixes" it wrongly later.
- Deterministic simulation matters: a test that needs a real config failure
  will be flaky. Prefer adding a narrow seam to `RunGoalLoopInput.deps`
  (e.g. `deps.resolveRuntime?`) over monkey-patching modules.
