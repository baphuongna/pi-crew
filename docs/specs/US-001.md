# US-001 — Lock-free event log rotation (lock-scope reduction)

## Status

verify-close — rotation machinery EXISTS; the "lock-free" promise is unmet.

## Lane / Priority

normal · P2

## Source

- `docs/stories/backlog.md` — Reliability epic, US-001 (planned).
- Current state verified 2026-09-22: `src/state/event-log/event-log-rotation.ts`
  already implements size-based rotation + streaming compaction
  (`compactEventLog`, `needsRotation`), but it is **lock-held**: the read-
  compact-write-recover sequence wraps `withEventLogLockSync`
  (comment at `event-log-rotation.ts:174-178`: "Wrap entire read-compact-write-
  recover sequence in lock to prevent event loss during compaction").

## Problem

The backlog item promised "lock-free event log rotation". Reality: rotation
holds the append lock for the whole read-compact-write cycle, so during
rotation, `appendEvent*` callers block on the same lock. With a 4 MB /
50 000-event log, `forEachLineSync` (ST-11 streaming, 8 KB chunks) already
bounds memory, but the lock hold time still scales with log size +compaction
cost.

Two distinct concerns:
1. **Correctness** (why the lock exists): events appended between the
   read and the write are lost unless the writer cooperates. This is real
   and must be preserved (the "ST-11" comment documents exactly this race).
2. **Concurrency** (the unmet promise): the lock is a global log-wide
   mutex (`withEventLogLockSync`), so a busy writer starves readers/rotators.

## Goals / Non-goals

- Reduce lock hold time: rotate against a **snapshot** (bounded read under a
  short lock, compact offline, atomic swap) instead of holding the lock
  across the full cycle.
- Keep the no-event-loss guarantee. `applyCompactionUnlocked` already exists
  for callers that hold the lock (`event-log-rotation.ts:222`) — the new path
  must splice new events written AFTER the snapshot back into the compacted
  head.
- NOT in scope: moving the log to a different storage engine.

## Design

Anchor: `src/state/event-log/event-log-rotation.ts:136-240`, caller
`src/state/event-log/event-log.ts` (append path, lock acquisition sites).

Proposed two-phase rotation:

1. **Phase 1 (short lock)**: `withEventLogLockSync` → record
   `{ startOffset, snapshot events, tailEventsAfterSnapshot: [] }` by reading
   the current file up to EOF. Release the lock immediately.
2. **Phase 2 (no lock)**: compact the snapshot in memory
   (`applyCompactionUnlocked` on the in-memory copy). This is the expensive
   part — now outside the lock.
3. **Phase 3 (short lock, conditional)**: re-acquire; read events written
   since the recorded offset (`tailEventsAfterSnapshot`); write compacted
   snapshot + tail atomically (single `atomicWriteFile`); replace the path.

Race window: between phase 1 and 3, an append lands in the tail. Phase 3
re-reads from the recorded offset — nothing lost. Two rotators racing: guard
with a per-path "rotation in progress" flag (or an `O_EXCL` sentinel) so the
second one aborts with `needsRotation() === false` after the first swap.

## Acceptance Criteria

1. During a rotation run, an `appendEvent*` concurrent with phase 2 is never
   dropped (tail splice preserves it).
2. Two concurrent `compactEventLog` calls on the same path: exactly one
   wins; the loser returns `undefined` (or a no-op result) without error.
3. Existing single-threaded rotation behavior (no concurrent appends) is
   byte-identical: compacted output equals current `compactEventLog` output
   on the same input.
4. Lock hold time per rotation is bounded (`O(snapshot read)`), not
   `O(log size + compaction)`. Prove with a test that asserts the lock is
   released while compaction runs (e.g. an append succeeds mid-rotation).

## Notes

- If the two-phase design proves racy under the existing writer (writers
  hold the SAME lock, so a writer between phase 1 and 3 is impossible — the
  lock is exclusive), then simply moving the COMPACTION out of the lock and
  keeping the swap under a fast lock already delivers the win. The sentinel
  flag alone then covers the writer-vs-rotator case without phase-3 splice.
  Simplest correct version first; splice only if a test proves it needed.
- Close-out evidence to attach: before/after lock-hold microbenchmark.
