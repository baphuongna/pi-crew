# US-011 — Stream-based event log for large runs

## Status

verify-close — the streaming READ half is already shipped (ST-11
`forEachLineSync`, 8 KB bounded chunks, `event-log-rotation.ts:11-38`).
Residual scope below.

## Lane / Priority

normal · P3

## Source

- `docs/stories/backlog.md` — Performance epic, US-011 (planned).

## Problem (as originally written)

"Stream-based event log for large runs." Large runs (50 000 events / 4 MB)
caused the whole-file `readFileSync` + split + parse approach to spike
memory and hold the append lock for the full read.

## What already exists (2026-09-22 verification)

- `src/state/event-log/event-log-rotation.ts:11-38` — `forEachLineSync`:
  bounded 8 KB chunk read, interleaved parse, works on rotation/compaction.
- ST-11 also covers the compaction evaluation path.

## Residual gap

1. **Reading** for OTHER consumers (event replay in `run-snapshot-cache`,
   transcript viewers, `handleGet` events) may still use whole-file reads.
   Audit `readFileSync(events)` call sites: if they exist for large logs,
   route them through `forEachLineSync`-style streaming.
2. **Appending** is already O(1) (append to fd) — verify no path re-reads
   the whole file to append.
3. Add a perf guard test: a 50k-event log is reconstructed/compacted under
   a bounded memory ceiling (assert via a counter, not RSS which is flaky).

## Acceptance Criteria (residual)

1. No `readFileSync(eventsPath)` left in the hot read paths (grep evidence
   in the PR).
2. All event consumers (replay, snapshot cache, transcript) use the stream
   reader; behavior identical.
3. New benchmark-test: 50k-event log compacts in < 2 s and the reader holds
   at most O(chunk) lines in memory at once (instrumented).
