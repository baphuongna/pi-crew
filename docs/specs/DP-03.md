# DP-03 — CI test sharding (4-shard matrix)

## Status

planned

## Lane / Priority

normal · P1 (CI budget is about to be breached)

## Source

- `docs/stories/backlog.md` — "Deferred — performance deep-dive 2026-09-18".
- Measured 2026-09-22: unit suite = **8,077 tests**, wall-clock ≈ **20 min**
  locally at concurrency 4; CI is clamped to concurrency **2**
  (`scripts/test-runner.mjs:158-171` — Windows Defender EPERM/EBUSY +
  macOS tmp contention flake storm from Rounds 13/14). Budget is 1500 s;
  the suite is about to exceed it.

## Problem

CI cannot go faster by raising `--test-concurrency` (deliberately clamped at
2 for cross-platform stability — documented in the runner). The only lever
left is **sharding**: split the suite across parallel jobs, each with its own
filesystem, so the per-FS contention that forced the clamp does not apply
across jobs.

## Goals / Non-goals

- Split the unit suite into **4 shards** (by top-level directory under
  `test/unit/`, balanced by measured wall-clock, not by file count).
- Each shard = its own CI job (own runner FS) → the clamp stays per-shard.
- Keep a single aggregate status check ("unit-tests") required by branch
  protection (so the required-check list doesn't change per shard).
- NOT in scope: raising the clamp value (revisit only after shards prove
  stable for a few weeks); Windows/macOS re-tuning beyond keeping the clamp.

## Design

Anchors: `scripts/test-runner.mjs` (accepts a glob; clamp at `:158-171`),
`.github/workflows/ci.yml` (the unit job), `test/unit/**` layout.

Steps:

1. `test-runner.mjs`: add `--shard=<i>/<n>` support (deterministic partition
   of the discovered file list — sort, then round-robin or contiguous
   balanced by a static weight table). Deterministic partition is critical
   so shards are reproducible and failures map to one shard.
2. `ci.yml`: `strategy.matrix.shard: [0,1,2,3]`, each job runs
   `node scripts/test-runner.mjs --shard=<i>/4 'test/unit/**/*.test.ts'`.
   Integration tests: either pinned to shard 0 or a 5th job (decide; prefer
   a separate job because they have a different timeout profile).
3. Aggregate job `unit-tests` (`needs: [unit]`) that fails if any shard
   failed → single required check.
4. Balance table: measure per-directory wall-clock once, commit the weights
   (comment where they came from), and add a test that asserts the weights
   cover every discovered directory (so adding a dir without a weight fails
   loudly rather than silently unbalancing).

## Acceptance Criteria

1. `--shard=i/4` is deterministic: two runs of the same shard select exactly
   the same file set.
2. Union of the 4 shards == full suite (no test skipped): a test asserts the
   partition covers 100% of discovered files exactly once.
3. CI wall-clock per job ≈ suite/4 (±20%) with the committed weights.
4. Branch protection still has ONE required unit check.
5. No test becomes flaky because of sharding (verify with 3 consecutive CI
   runs before removing the old single-job path).

## Validation

| Layer | Test | Expected |
|-------|------|----------|
| Unit | `test/unit/scripts/shard-partition.test.ts` (new) | determinism, full coverage, no duplicates, weights complete |
| CI | 3 consecutive green runs (all shards) | stable |
| Timing | record per-shard wall-clock | ≈ balanced |
| Gates | `npm run test:critical` · `npm run typecheck` · biome | green |
