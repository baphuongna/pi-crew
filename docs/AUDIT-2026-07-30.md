### SEC-3 | Medium | Effort S — Redaction fail-open (CỐ Ý): PEM secrets leak past 100 markers hoặc 2MB

🔧 **VERIFIED-CORRECTION:** Hành vi fail-open là **THẬT** nhưng là **thiết kế có chủ đích (intentional)**, KHÔNG phải "regression của F-05" như ghi ban đầu. Code comment ghi rõ "F-05 hardening" + đã có test regression. Đánh giá lại severity High→Medium (trade-off DoS-resistance cần quyết định lại, không phải bug vô tình).

**File:** `src/utils/redaction.ts:272-280` (đính chính: audit gốc ghi `:326-337` — sai; `:326` là hàm `redactInlineSecrets` không liên quan)

```ts
// Replace PEM private keys. Skip the regex entirely on very large inputs —
// no real PEM key exceeds ~7KB ... (comment "F-05 hardening")
if (result.length <= 2_000_000) {
    const beginMarkerCount = result.split("-----BEGIN").length - 1;
    if (beginMarkerCount <= 100) {
        result = result.replace(PEM_PRIVATE_KEY_PATTERN, "***");
    }
}   // else: NO PEM redaction (cố ý — ưu tiên chống DoS)
```

**PoC đã xác nhận:**
```
[baseline <=100 markers] key redacted: true
[101 BEGIN markers] key LEAKS: true
[>2MB input] key LEAKS: true
```

Output >2MB hoặc >100 `-----BEGIN` markers → PEM redaction **skipped entirely** → private key có thể lọt verbatim vào events.jsonl, artifacts, logs, export bundles. **Đây là fail-open có chủ đích** (comment + test `redaction-redos-regression.test.ts` #4/#5 ghi rõ intentional: ưu tiên bound CPU ~50ms cho adversarial marker flooding).

**Nuance:** PEM là pattern duy nhất fail-open; các redaction khác (Bearer, JWT, inline secrets) vẫn chạy. Threat model: PEM private key nằm trong output >2MB (hiếm).

**Fix (trade-off decision, không phải bug fix):** Nếu muốn defense-in-depth, fail **closed** (replace oversized region với `***`) hoặc dùng linear `indexOf("-----BEGIN")` → `indexOf("-----END", i)` window scan O(n) không cần cap. Cân nhắc: mất DoS-resistance bound hiện tại.
**Test gap:** KHÔNG — hành vi ĐÃ được test (`redaction-redos-regression` #4/#5). Audit gốc ghi "test gap: yes" là SAI.

### SEC-4 | Medium | Effort S — Polynomial O(n²) DoS trên project agent files (KHÔNG phải ReDoS)

🔧 **VERIFIED-CORRECTION:** Regex + 7 call sites + thiếu file-size cap đều **ĐÚNG**. Nhưng nhãn "ReDoS" **SAI** — không có nested quantifier / overlapping alternatives nên không catastrophic exponential backtracking. Đây là **polynomial O(n²) DoS**. Chính PoC timing của audit chứng minh: 80K→971ms, 160K→3866ms, 320K→15434ms ≈ **4× input → ~4× time = quadratic**, không phải exponential. Severity High→Medium.

**File:** `src/agents/discover-agents.ts:320,340` (regexes xác nhận chính xác tại các dòng này)

```ts
sanitized = sanitized.replace(/<!--[\s\S]*?-->|<\/?script[^>]*>/gi, "");
sanitized = sanitized.replace(/```\s*(?:system|instruction|prompt)\n[\s\S]*?```/gi, "");
```

Lazy quantifier `[\s\S]*?` + flag `/g` trên input nhiều `<!--` không có `-->` → engine retry từ mỗi vị trí `<!--`, scan tới cuối → O(markers × length) = O(n²). Không file-size cap. `readAgentDir` reads every `.md` không limit.

**PoC đã xác nhận (quadratic, không exponential):**
```
agentfile bytes= 80000  elapsed=  971ms
agentfile bytes=160000  elapsed= 3866ms
agentfile bytes=320000  elapsed=15434ms      # 4× bytes → ~4× time = O(n²)
```

Cũng tìm thấy tại 7 call sites khác trên untrusted content: `src/config/markers.ts:52`, `src/runtime/prose-compressor.ts:17`, `src/runtime/output-validator.ts:23`, `src/runtime/adaptive-plan.ts:71,75`, `src/runtime/result-extractor.ts:130`, `src/runtime/task-runner/output-splitter.ts:52`, `src/ui/transcript-viewer.ts:80`. (Lưu ý: adaptive-plan/result-extractor/output-splitter/transcript-viewer chạy trên output do hệ thống sinh, risk thấp hơn agent-file/markers.)

**Fix:** Cap agent-file reads (256KB), bound quantifiers `{0,8192}?`, short-circuit bỏ qua file vượt cap.
**Test gap:** yes — không có test adversarial/large-input cho sanitizer.

### RT-1 | P1 | Effort M — Scheduler early-returns clobber in-flight tasks thành `skipped`

🔧 **VERIFIED-CORRECTION (vòng 3, re-verify bằng code):** Race là **THẬT** và window là **toàn bộ thời gian in-flight**, KHÔNG chỉ pre-persist như đính chính vòng 2 ghi:
> - `handleFailedTask` dùng `ctx.tasks` in-memory (stale): in-flight task vẫn là `"queued"` trong `ctx.tasks` cho tới khi unit settle và `mergeUnitResult` chạy.
> - `saveRunTasksAsync` (`state-store.ts:514-523`) ghi thẳng `ctx.tasks` qua `atomicWriteJsonAsync` — **không re-read disk, không merge**. Vì vậy worker B đã persist `"running"` lên disk rồi VẪN bị ghi đè thành `"skipped"`.
> - Đính chính vòng 2 nhầm lẫn merge path bình thường (`mergeUnitResult` → giữ `running`) với early-return path này (không có merge).
> - Đúng: worker bị `drainPendingUnits` abort đúng (không orphan). Tác hại thực = task in-flight bị lãng phí + thành `skipped`; `team resume` không re-queue `skipped` (chỉ filter failed/cancelled) → **work loss**.

**File:** `src/runtime/team-runner.ts:1133` (và `:1911`)

```ts
ctx.tasks = markBlocked(ctx.tasks, `Blocked by failed task '${failed.id}'.`);
await saveRunTasksAsync(ctx.manifest, ctx.tasks);
ctx.manifest = updateRunStatus(ctx.manifest, "failed", `Failed at task '${failed.id}'.`);
return { kind: "return", result: { manifest: ctx.manifest, tasks: ctx.tasks } };
```

`markBlocked` chỉ maps `queued → skipped`. Trong streaming dispatch, in-flight task vẫn là `"queued"` trong `ctx.tasks` (stale) bất kể worker đã persist `"running"` lên disk hay chưa. `saveRunTasksAsync` ghi đè disk state (kể cả `"running"`) thành `skipped`. `drainPendingUnits` (chạy trong `finally`, SAU return) abort worker nhưng **không merge** kết quả đã settle.

**Failure scenario:** 3-task parallel batch, A fail khi B đang chạy. B thành `skipped` (bất kể đã persist `running` chưa), không được chạy lại; nếu B vừa settle trong window đó, kết quả bị drop.

**Fix:** Before `saveRunTasksAsync`, `await drainPendingUnits(...)` và merge settled results. Dùng `cancelNonTerminalTasks` thay vì `markBlocked` cho in-flight IDs.
**Test gap:** yes — không có test "failed task while siblings in flight".
