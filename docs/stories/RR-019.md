## 1. Vấn đề

Hai phát hiện độc lập, gộp theo đợt 3:

- **F14** là lỗi hiệu năng UI: cơ chế dừng render khi idle (R1) đã có, nhưng nguồn
  `schedule()` từ preload polling vô hiệu nó — nên mọi session có run đang mở vẫn render
  mãi khi không có gì thay đổi.
- **F17** là lỗi chất lượng đầu ra: hai chỉ dẫn verification mâu thuẫn nhau được inject vào
  **cùng một prompt**, không có quy tắc precedence, và cache evidence không có provenance.

### F14 — Preload polling vô hiệu cơ chế dừng render khi idle

**Vấn đề.** Mỗi lần `buildFrame()` thành công, `backgroundPreload` gọi `schedule()` —
**không** so sánh dữ liệu trước/sau. `buildFrame()` trả `true` mỗi khi `ctx.currentCtx` tồn
tại, không có data comparison. `schedule()` reset idle counter, re-arm fallback timer, và
re-arm vòng fallback loop mà `fallbackLoop()` vừa dừng có chủ đích (R1) — nên idle stop
không bao giờ chạm tới.

**Vị trí.**

- `src/extension/registration/lifecycle-handlers.ts:727-731` — `buildFrame().then((ok) => {
  preloading = false; if (ok) ctx.renderScheduler?.schedule(); })`.
- `src/extension/registration/lifecycle-handlers.ts:684` — `if (!ctx.currentCtx) return false;`
  và `:721` — `return true;`: `buildFrame` không so sánh dữ liệu.
- `src/ui/render-scheduler.ts:142-154` — `schedule()` set `lastEventAt = Date.now()`,
  `idleFallbackRenders = 0`, `consecutiveCapHits = 0`, rồi re-arm `fallbackTimer` nếu đã dừng.
- `src/ui/render-scheduler.ts:115-146` — `fallbackLoop()` là nơi R1 dừng loop sau
  `maxIdleFallbackRenders`; comment R1 trong chính `fallbackLoop()` giải thích chính xác cơ
  chế bị vô hiệu ("...unlike the old code which called schedule() here and thereby reset
  lastEventAt, self-perpetuating a ~fallbackMs render loop forever").

**Bằng chứng đo** (cửa sổ idle 12 s, default `maxIdleFallbackRenders = 8`, `fallbackMs = 1000`):

```text
scheduler đơn lẻ        → 8 render rồi dừng hẳn
có preload wiring thật  → 11 render và vẫn tiếp tục
```

Test hiện có `test/unit/ui/render-scheduler.test.ts:166-214` chạy scheduler với
`events: undefined` và **không có caller preload** → không bao giờ thấy lỗi này.

**Hướng sửa.**

1. Chỉ gọi `schedule()` khi dữ liệu **thực sự** đổi: so sánh version/signature của snapshot
   (theo tiền lệ signature cache đã có trong widget) trước khi schedule.
2. Tách "maintenance refresh" khỏi "genuine activity": preload idle không được coi là hoạt
   động của người dùng; nếu cần refresh định kỳ thì đi đường `invalidate()` không reset
   `lastEventAt`.
3. Giữ nguyên animation tick khi thực sự có công việc (không được biến F14 thành "tắt render").

### F17 — Verification prompt mâu thuẫn, cache không provenance

**Vấn đề.** Agent body (`agents/verifier.md`) ra lệnh chạy **full** `npm test`; workflow
verify step ra lệnh ngược lại và cấm full suite. Cả hai được inject vào cùng một prompt,
không có quy tắc precedence. Ngoài ra: cache không ràng buộc với phiên bản mã/command/môi
trường, `tee` không bảo toàn exit code của npm, và cleanup wildcard xoá log của verifier khác.

**Vị trí.**

- `agents/verifier.md:21-23` — "Run the full test suite ONCE and save output to a cache file:
  `npm test 2>&1 | tee .crew/cache/verify-test-$(date +%s).log`" (verification ghi rõ
  `:16,21-23`).
- `agents/verifier.md:47` — rule "If you already have a cached log, READ it" **không** ràng
  buộc cache với commit/command/môi trường.
- `agents/verifier.md:42` — `rm -f .crew/cache/verify-test-*.log` (wildcard).
- Workflow cấm full suite: `workflows/fast-fix.workflow.md:24`,
  `workflows/plan-execute.workflow.md:30`, `workflows/review.workflow.md:31`,
  `workflows/strict-fast-fix.workflow.md:26`, `workflows/distill.workflow.md`.
- Inject vào cùng prompt: agent body → system prompt qua
  `src/runtime/model/pi-args.ts:341-348`; workflow section → task arg qua
  `src/runtime/task-runner/prompt-builder.ts:334`. Không có quy tắc override
  (`grep` trong `prompt-builder.ts` → 0 hit).
- `src/workflows/discover-workflows.ts:259-264` — workflow builtin được nạp từ
  `packageRoot()/workflows` (dòng 261), nên repo không phải Node vẫn nhận command npm nguyên văn.

> **Hiệu chỉnh bắt buộc (C1, verification §3).** Review gán nhầm vị trí: các command
> hardcode `npm run test:critical` / `npx tsc --noEmit` **KHÔNG** nằm trong
> `agents/verifier.md` (`grep -n "test:critical\|tsc --noEmit" agents/verifier.md` → **0 kết
> quả**). Chúng nằm trong `workflows/*.workflow.md` — cụ thể `fast-fix:24`,
> `plan-execute:30`, `review:31`, `strict-fast-fix:26`, `distill:147,160,176`. Mâu thuẫn thì
> vẫn đúng và đã xác nhận; chỉ vị trí gán là sai. Packet này ghi đúng vị trí.

**Bằng chứng đo:**

| Hạng mục | Kết quả |
|---|---|
| Provenance trong agent body | `grep -n "version\|env\|sha\|git\|HEAD" agents/verifier.md` → **0 hit** |
| Log trong `.crew/cache` | 51 log, trong đó **7 `verify-test-*.log`** từ các lần chạy trước |
| `tee` exit code | `bash -c 'false \| tee /dev/null; echo $?'` → **0**; với `pipefail` → **1** |
| `pipefail` trong repo | `grep -rn pipefail` → **0 hit** |
| Wildcard cleanup | `:42` khớp **mọi** log verifier trong thư mục đang thực sự chứa nhiều log như vậy |

**Hướng sửa.**

1. Một verification plan **thống nhất**, suy ra từ project scripts/instructions — không
   hardcode command npm trong workflow của một extension tổng quát.
2. Quy tắc precedence tường minh giữa agent body và workflow verify step (workflow thắng,
   hoặc agent body chuyển thành "đọc plan từ project").
3. Artifact verification ghi: command, exit code, git revision + working-tree fingerprint,
   dependency/env fingerprint, thời điểm.
4. Chỉ reuse cache khi provenance còn khớp; sau khi sửa mã phải kiểm chứng lại.
5. Bảo toàn exit code (`set -o pipefail` hoặc không pipe qua `tee`).
6. Mỗi attempt chỉ quản lý log của chính mình (không wildcard xoá log của người khác).

## 4. Acceptance Criteria

**F14 — idle render**

1. **AC-1.** Với fake clock, tích hợp preload wiring + scheduler thật, dữ liệu **không đổi**
   trong cửa sổ ≥ 12 s: số render **bằng** số render của scheduler đơn lẻ (8 với default
   `maxIdleFallbackRenders = 8`, `fallbackMs = 1000`), và vòng render **dừng** (không còn
   timer armed).
2. **AC-2.** Một snapshot **thay đổi** trong cùng cửa sổ idle → render được kích hoạt lại,
   và counter idle được reset đúng một lần (không tạo vòng lặp vô hạn).
3. **AC-3.** Preload idle không reset `lastEventAt` của scheduler: sau khi preload tick chạy
   N lần với dữ liệu không đổi, `idleFallbackRenders` không bị đưa về 0.
4. **AC-4.** Khi thực sự có run đang chạy và snapshot đổi, animation tick vẫn hoạt động —
   không hồi quy sang "đứng hình".
5. **AC-5.** Test tích hợp dùng **preload wiring thật** (không chỉ scheduler đơn lẻ), và
   **fail** trên baseline `0b9fa771` (chứng minh nó bắt được lỗi).

**F17 — verification quality**

6. **AC-6.** Không còn mâu thuẫn: với mỗi builtin workflow có verify step, `grep` cho thấy
   hoặc (a) không còn lệnh cấm/khuyến nghị full suite nào trong cả `agents/verifier.md` và
   workflow, hoặc (b) có một quy tắc precedence tường minh xuất hiện trong prompt cuối cùng
   (kiểm bằng test render prompt thật, không chỉ grep file).
7. **AC-7.** Command verify **không** hardcode `npm`/`npx` trong `workflows/*.workflow.md`
   cho repo không phải Node: test với fixture repo Node **và** fixture repo Python (hoặc
   fixture không có `test:critical`) — plan verify được suy ra phù hợp, không xuất hiện
   `npm run test:critical` nguyên văn trong repo không phải Node.
8. **AC-8.** Artifact verification chứa đủ trường: `command`, `exitCode`, `gitRevision`,
   `workingTreeFingerprint`, `dependencyFingerprint`, `envFingerprint`, `timestamp`.
   Test assert trên artifact thật do verify step sinh ra.
9. **AC-9.** Reuse cache chỉ xảy ra khi provenance khớp: test thay đổi source (hoặc
   `gitRevision`/fingerprint) sau khi cache được tạo → cache **không** được reuse.
10. **AC-10.** Exit code được bảo toàn: test chạy command fail qua pipeline ghi log mà
    wrapper **không** trả 0. Bao gồm cả case command không tồn tại.
11. **AC-11.** Cleanup log không dùng wildcard toàn thư mục: test tạo log của "attempt khác"
    trong cùng thư mục cache, chạy cleanup của attempt hiện tại, assert log của attempt khác
    **còn nguyên**.

## 5. Design Notes

- **Commands:**
  - `node scripts/test-runner.mjs test/unit/ui/<test-moi>.test.ts`
  - `node scripts/test-runner.mjs test/unit/runtime/verification/<test-moi>.test.ts`
  - `npm run typecheck`
  - `npm run test:critical`
  - `npm run test:unit`
  - `npm run lint && npm run format:check`
  - `npm run build:bundle` (bắt buộc — bundle là đường load mặc định)
  - `npm run ci`
- **State changes:** F14 chỉ thêm state trong RAM (signature/version của frame đã dựng).
  F17 thêm file artifact verification — đề xuất theo mẫu `.crew/cache/` đang dùng nhưng
  **tên file chứa identity của attempt** để không đụng nhau (thay cho
  `verify-test-$(date +%s).log` + wildcard cleanup).
- **API changes:** `buildFrame()` đổi từ `Promise<boolean>` sang trả thông tin "có thay đổi
  hay không" (ví dụ `Promise<{ changed: boolean; signature: string }>`) — đây là API nội bộ
  của `lifecycle-handlers.ts`, không phải contract công khai. `RenderScheduler.schedule()`
  giữ chữ ký; thêm đường `invalidate()`-only cho maintenance refresh (nếu cần).
- **Đo lường:** F14 dùng fake clock như `test/unit/ui/render-scheduler.test.ts:166-214` đang
  làm, nhưng phải đi qua **preload wiring thật**. F17 đo bằng cách render prompt thật và
  đọc artifact thật.
- **Alternative bị bác:**
  - *Tăng `maxIdleFallbackRenders` hoặc `fallbackMs`.* Không sửa nguyên nhân: preload vẫn
    reset counter mỗi tick, chỉ làm vòng lặp thưa hơn. Review nói rõ vấn đề là **nguồn**
    schedule, không phải ngưỡng.
  - *Tắt hẳn preload khi idle.* Làm UI không cập nhật khi có thay đổi ngoài dự kiến (run
    mới xuất hiện do session khác) — mất tính năng, không phải tối ưu.
  - *So sánh sâu (deep-equal) toàn bộ snapshot trước khi schedule.* Đắt hơn cả việc render
    ở kích thước snapshot hiện tại; signature/version là mức đủ (tiền lệ đã có trong widget
    signature cache).
  - *Chỉ xoá dòng "run full `npm test`" khỏi `agents/verifier.md` và để nguyên workflow.*
    Không giải quyết tính không di động: repo không phải Node vẫn nhận `npm run test:critical`
    nguyên văn qua `discover-workflows.ts:259-263`.
  - *Chỉ thêm `set -o pipefail` vào lệnh `tee`.* Sửa được một nửa exit code nhưng không đụng
    provenance cache, wildcard cleanup, hay mâu thuẫn prompt — và `pipefail` là bash-ism,
    không di động sang mọi shell.
  - *Dùng cold verifier cho mọi gate.* Review loại trừ rõ: cold verifier chỉ cho high-risk
    gate, không bắt mọi task trả toàn bộ chi phí đó.
